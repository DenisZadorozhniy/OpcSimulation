## Реальный HTTP AQI

Исследовано 11 октября 2026 года через установленный Chrome и Playwright.
Поиск: `https://search.waqi.info/nsearch/world/London`.
Обновление London: POST `https://api2.waqi.info/api/feed/@5724/aqi.json`.
Это HTTP JSON, а не WebSocket. В ответе `rxs.obs` содержит запись `status: ok`,
её `msg.aqi` — числовое измерение, `msg.idx` — 5724.

При первой загрузке AQI уже находится в HTML. Клиентский updater получает JSON,
но применяет его только при более свежем `msg.xsync.gen`, чем версия HTML-кэша.
На исследованном сайте HTML и API иногда содержали различные версии измерения.
Перехват оставляет реальный baseline AQI неизменным и повышает только `xsync.gen`,
чтобы проверять именно JSON → UI, а не случайное совпадение со старым HTML.
Подменённые ответы копируют реальный envelope и метаданные; структура не выдумана.
Обновление запускается через обнаруженную функцию сайта `updateAqiWidgetAndForecast(5724)`
в Page Object. Функция действительно отправляет HTTP и выполняет штатный рендеринг;
DOM и функция рендеринга тестами не подменяются. Это привязка к внутреннему API сайта.

Поиск использует клавиатурные события: `fill()` без keyup не запускал запрос.
Используется `pressSequentially()` без искусственной задержки.
Основные локаторы ограничены `#citydivmain`, потому что сайт дублирует ID виджета
в скрытых копиях. Результат выбирается по `london; london, united kingdom`,
а не только по флагу GB.

## API и состояния

Публичный REST API является только хранилищем. Правила находятся в клиенте:
новый объект может иметь только `provisioned`; обновление прошивки переводит
`provisioned → active`; повторное обновление прошивки сохраняет `active`;
телеметрия разрешена в `active`; DELETE разрешён только из `active`.
После DELETE ID исключается из набора собственных объектов, повторные изменения отклоняются.
«firmware-updated» — событие обновления и поле версии, а не дополнительный статус:
задание явно ожидает `status: active` после прошивки.
Состояние decommissioned представлено отсутствующим объектом (GET 404).

PATCH отправляет полное `data`, сохраняя `model`, `sensor_type` и `lastReading`.
Ответы проверяются во время выполнения. Любая мутация требует собственного ID,
созданного этим экземпляром клиента. Очистка в teardown удаляет только такие ID,
обходя guard состояния исключительно для уборки ресурсов при неуспешном сценарии.
Если сеть пропадёт после POST до получения ID, гарантировать удаление невозможно.

## OPC UA

Использован уже работающий локальный сервер `opc.tcp://localhost:50000`.
`ns=3;s=StepUp` возвращает UInt32 (`ns=0;i=7`) и меняется.
Запись выполнена в встроенный узел `ns=3;s=FastNumberOfUpdates`:
Int32 (`ns=0;i=6`), UserAccessLevel=3 (CurrentRead + CurrentWrite).
Дополнительный JSON NodeList не требуется. Исходное значение восстанавливается
и повторно читается в `finally`; узел влияет на симуляцию, поэтому worker один.

Клиент проверяет statusCode, возвращает browse-данные, хранит подписки,
закрывает сессию с удалением подписок и отключает транспорт даже при ошибке закрытия.
Ошибки уведомлений накапливаются для проверки, а не выбрасываются из event handler.
PKI находится в игнорируемом `tmp/opcua-pki`; applicationUri согласован с applicationName.
Не включён chaos: случайные отключения делают обязательные проверки нестабильными.
Незащищённый транспорт используется только для стенда из задания.

При завершении подписок локальный сервер выдавал `BadNoSubscription` с
`requestHandle=0`; node-opcua выводил диагностические сообщения о несовпадении
requestHandle. Операции закрытия разрешались, все восемь OPC UA тестов прошли.
Диагностика не подавляется. Поведение серверных ресурсов не проверяется через
административные счётчики: проверяются завершение cleanup, локальный реестр и отказ чтения.

## CI и воспроизводимость

GitHub Actions устанавливает зависимости через lockfile, выполняет ESLint с
`--max-warnings=0`, Prettier, typecheck, сборку, устанавливает Chromium,
запускает Microsoft OPC PLC и ожидает успешное OPC UA чтение через ограниченный poll.
Затем запускает четыре обязательных проекта и дополнительный проект `clients`,
сохраняя отчёты даже при падении.
Падения внешнего сайта не скрываются через skip, expected failure или continue-on-error.
Образ `latest` следует заданию; для устойчивого долговременного CI стоит закрепить digest.
Workflow пока не запускался на GitHub.
Холодный запуск той же Docker-команды проверен локально в отдельном контейнере
на порту 50001: readiness создал сессию, прочитал числовой узел и отключился.
Временный контейнер остановлен; исходный `opcplc` на 50000 не изменялся.

У репозитория нет исходного коммита (HEAD отсутствует). Невозможно ответвиться
от базового коммита без создания истории. Коммиты, push и PR не выполнялись.
Это часть процесса сдачи, требующая отдельного разрешения пользователя на публикацию.

### Подтверждённые ограничения

1. При `{}` и HTTP 503 aqicn.org сохраняет старое числовое значение без видимой ошибки.
   Требование graceful handling для этих сценариев **не выполнено внешним сайтом**.
   Тесты остаются падающими. Некорректное AQI-значение вызывает метку `no data` и проходит;
   отдельного блока ошибки нет (уточнено при последующем исследовании).
2. Публичный API исчерпал квоту. Диагностический GET вернул HTTP 405 и JSON:
   «50 requests per 24 hours». В последнем полном запуске упали API lifecycle
   (включая cleanup) и POST в integration. Это не успешные результаты.
3. Не удалось удалить собственный объект `ff808181a09d98f701a12a9f70e83bfc` из-за той же квоты.
   Квитанция сохранена в `tmp/device-receipts.json`. После восстановления доступа:
   `npm run build`, затем `npm run cleanup:devices`.
4. CI workflow создан и Docker/readiness проверены локально; GitHub Actions не запускался.
   CI будет честно красным при воспроизведении известных дефектов сайта или исчерпании квоты.
5. Обязательные сценарии реализованы, но утверждать полное соответствие по результатам

### Исследование причин empty / missing / http-error

11 октября 2026 года выполнено дополнительное исследование в видимом Chrome.
Исследован свежий JavaScript сайта
`https://aqicn.org/air-cache/header/bundle.min.js?_=20250121.173557`,
записаны ответы браузера, запросы, сообщения консоли, DOM и `getWidgetAqiGraphModel()`.
Диагностика использует отдельный BrowserContext для каждого сценария; повторена с явно
отключённым HTTP-кешем через CDP и заблокированными Service Worker. Контроллера Service Worker нет.
В диагностике использован прямой переход на London; затем четыре штатных теста повторены
с исходной fixture, которая выполняет поиск города. Результаты совпадают.

#### Доставка и жизненный цикл

Перехватывается POST `https://api2.waqi.info/api/feed/@5724/aqi.json`.
Браузер действительно получил 200 `{}`, 200 с `aqi: null`, 200 с
`aqi: 'invalid-sensor-value'` и 503 `{ error: 'Telemetry unavailable' }` соответственно.
После проверки реального baseline fixture ожидает окончания исходных AQI-запросов.
Реальные ответы не пропускаются поверх подмены: установленный route продолжает обрабатывать
все совпадающие запросы. В диагностическом окне после смены сценария не обнаружено другого
источника, который записал бы прежнее числовое AQI обратно в основной виджет.
Запросы `forecast.json` происходят после успешно преобразованного измерения для missing/invalid;
они обновляют прогноз, а не значение основного AQI. После их выполнения модель для missing
по-прежнему содержит null. Сохраняется именно ранее отрисованный DOM, а не результат нового
успешного запроса или браузерного кеша.

#### Подтверждённые причины

| Сценарий   | Обработка приложением                                                                                                                                                                                                                                              | Видимый результат                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| empty      | HTTP-парсер возвращает `{}`; преобразование измерения в `updateAqiWidgetAndForecast` пытается выполнить `t.city.idx = t.idx` при отсутствующем city и выбрасывает TypeError. Catch пишет `Failed to update the AQI` только в консоль. Модель и DOM не обновляются. | Старое число 34, статус Good, прежнее Updated; нет ошибки или пустого состояния.                              |
| missing    | Ответ принят, версия `xsync.gen` выше baseline; внутренняя модель обновлена до `aqi: null`. DOM helper внутри `updateWidgetAqiGraph` использует `if (e) o.innerHTML = e`, поэтому null не очищает прежний текст AQI.                                               | В модели null, на экране по-прежнему 34 и Good; предупреждения нет.                                           |
| http-error | HTTP helper вызывает `response.json()` без проверки HTTP-статуса. JSON ошибки доходит до преобразования измерения, где отсутствующий city вызывает такой же TypeError. Catch ограничивается console.error.                                                         | Старое число 34 и Good без сообщения о неуспешном обновлении.                                                 |
| invalid    | Непустая строка проходит в модель и DOM. Функция определения категории AQI выбирает `no data` для нечислового значения.                                                                                                                                            | Вместо числа отображается `invalid-sensor-value`, рядом видимая метка `no data`; тест проходит по этой метке. |

Предыдущее объяснение, что invalid показывает отдельный блок ошибки, было неточным.
Подтверждён именно статус `#citydivmain #aqiwgtinfo` с текстом `no data`; `.ui.error` и
`[role=alert]` не появились. Этот тест проверяет сигнал недоступности, а не чистое оформление
плейсхолдера: вывод сырой строки `invalid-sensor-value` остаётся особенностью внешнего сайта.
Console.error в empty/http-error перехватывается приложением, поэтому пустой `pageErrors`
не означает отсутствие внутренних ошибок и не подтверждает корректное пользовательское поведение.

#### Автоматизация и соответствие PDF

Оригинальный TC1 требует, чтобы потерянный сигнал обрабатывался без вводящих в заблуждение
старых данных: среди примеров есть error/empty state. Поэтому падение при сохранении 34/Good
без предупреждения соответствует заданию. `missing` с null — дополнительная проверка того же
контракта; этот конкретный JSON-вариант в PDF отдельно не предписан.

В автоматизации не обнаружено причины, которая объясняла бы эти три падения неверной подменой
или кешем. Уточнена проверка unavailable: `no data` теперь проверяется только в статусе основного
AQI, а не в произвольном дочернем тексте города; скрытые элементы не считаются сигналом.
Видимая ошибка проверяется до обращения к значению, чтобы корректно обрабатывать замену виджета
ошибкой. Добавлен `AirQualityMock.expectScenarioDelivered`: перед проверкой UI он подтверждает
POST, завершение ответа, отсутствие Service Worker, ожидаемый HTTP-статус и подменённый JSON.
Assertions не ослаблены ради успешного результата.

Повторный штатный запуск:
`npx playwright test --project=ui --grep "should handle" --output=tmp/ui-delivery-audit`.
**1 прошёл (invalid), 3 упали (empty, missing, http-error)**. Во всех четырёх тестах проверки
доставки ответа прошли; три падения происходят в `expectUnavailableSignal()`.
TypeScript, ESLint, сборка и Prettier прошли.

Артефакты: `tmp/ui-delivery-audit` (traces/скриншоты), `tmp/aqi-audit.json`
(контрольный прогон без кеша и Service Worker), `tmp/audit-header.js` (исследованный код сайта),
`tmp/audit-{empty,missing,invalid,http-error}.png` (полные скриншоты).
В контрольной диагностике после снимка состояния отдельно вызывается штатный `aqisrv.obs2`
для проверки результата парсера; поэтому JSON содержит два подменённых AQI-ответа на сценарий.
Второй диагностический вызов не используется для обновления виджета или оценки assertion.
